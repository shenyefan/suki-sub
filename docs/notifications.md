# Telegram 通知

在 Worker 环境变量 `SUKI_SUB_PUSH_SERVICE` 配置推送服务后，前往设置页主动开启 Telegram 通知。新实例默认关闭总开关；关闭总开关后，订阅和组合单独开启的通知也不会发送。无法读取设置时保持静默。

## 分类与默认值

| 分类 | 默认值 | 范围 |
| --- | --- | --- |
| 订阅拉取 | 仅异常 | 客户端通过分享链接拉取订阅或组合；包括下载、解析、处理、输出失败，以及部分失败后仍完成请求的提醒 |
| 分享管理 | 关闭 | 创建、删除分享，以及分享链接无效、过期或次数用尽的访问异常 |
| 备份恢复 | 关闭 | 从备份恢复数据的结果 |
| 定时备份 | 仅异常 | 后台定时备份结果 |
| 登录与退出 | 关闭 | 登录回调和退出登录结果 |
| 系统故障 | 开启 | 其他未归类的服务端故障；不接收普通客户端错误和通知自身的发送失败 |

只有总开关使用开关控件，各分类统一使用下拉框。系统故障只提供关闭、开启；其余分类可选关闭、仅异常或全部。仅异常包括失败和警告。分类关闭后不会再由系统故障补发。

日常增删改、排序、导入、克隆、预览、节点解析、流量查询、保存设置、导出备份和手动备份不推送 Telegram，页面反馈与必要日志继续保留。

## 单个订阅与组合

编辑页的“拉取通知”可选跟随全局、关闭、仅异常、全部，缺省跟随全局的订阅拉取分类。资源级选择可覆盖该分类，总开关始终优先。关闭某个订阅的拉取通知不影响独立的分享管理通知。

组合只按组合自身的选项决定是否发送，不读取成员订阅的通知选项。成员的异常合并到本次组合请求的摘要中。

仅修改拉取通知不重新下载或解析上游，因此上游故障时也能关闭通知。修改来源、成员或操作管线仍执行完整校验。

## 限频与内容

每次请求最多发送一条摘要。相同资源、操作、结果和错误类型每 30 分钟最多尝试推送一次，成功与不同错误类型分别计时；同一资源的不同分享链接共用限频。无效分享链接统一限频，避免随机无效链接刷屏。

限频名额通过 D1 条件写入原子领取，跨请求、跨实例共用。完整初始化脚本 `migrations/0001_init.sql` 包含该表；已有实例在首次发送通知时由运行时自动建表，无需额外升级脚本。仅保存事件摘要哈希和过期时间，过期记录在下次领取时清理。发送失败也占用本轮名额，防止故障期间持续重试。

消息只展示事件、资源、时间、主要原因、请求编号等摘要。完整诊断在日志页查阅。Telegram 配置错误在设置页显示，发送失败写入日志；设置页展示最近一次发送失败的时间与原因，不再通过 Telegram 转发通知故障。

## 旧配置与验证

旧的显式关闭继续有效。旧的资源开启选项保留为仅异常或全部；没有资源级选项的资源改为跟随全局。旧总范围“仅异常”转成开启，各分类独立决定范围。已保存的对应分类值继续生效，已取消的日常操作分类不再参与分发。

使用 Node.js 22.15 或更新版本运行通知回归检查（使用仓库已有的 TypeScript 编译器和 Node SQLite，无需额外测试依赖）：

```bash
node --test tests/notifications.test.mjs
```

检查覆盖总开关、分类隔离、资源继承、组合摘要、页面操作静默、分享访问归类、部分失败、并发限频、设置读取失败和发送失败日志。Telegram 请求使用模拟响应，不向真实会话发送消息。
